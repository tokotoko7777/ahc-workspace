# 担当できる人で候補を絞り、同じ到着時刻の評価を共有する

**状態:** 汎用ライブラリへの提案。AHC008で選択の一致を確認したが、ソルバ全体の高速化の採用基準には届いておらず、既存の実装を置き換えていない。

## 使う場面

単独・ペアの仕事を列挙してから、使用する担当者が重ならない集合を選ぶ問題。たとえば、片方の入口だけを閉める仕事と、両方を同時に閉める仕事が混在し、それぞれに担当資格や立ち位置の制約がある場合。

1. 担当者全員の直積を作らず、役割ごとの候補リストを先に作る。
2. 単独の仕事は対応するリストを一度走査するだけ。ペアは左右の候補リストの直積だけを作り、同一担当者は除外する。
3. 同じ仕事で評価が到着時刻 `eta = max(準備時間, 左の到着, 右の到着)` のみに依存するなら、到着時刻ごとの評価を遅延計算して再利用する。個人別のコストや移動の組合せで変わる量はキャッシュに含めない。
4. 最終キー（評価値、仕事ID、役割ごとの担当IDなど）にゼロ埋めや並べ替えで意図しない変更を加えない。同点の順序が探索結果に影響する場合は従来と同じキーで整列する。

`M` 人で左右候補が `L` 人と `R` 人なら、資格確認を含むペア列挙は `O(M + L*R)`。全員が両方を担える場合や、すでに候補リストを持つ場合はほとんど効かない。

## AHC008の測定

- 1〜10人、最大32仕事の合成10,000状態で、選択した候補ID・担当ID・整数評価と順序が従来法と全件一致。
- 同じ合成状態10,000件を使い、列挙・整列・選択だけを8回ずつ交互に実行。中央値66.03→43.36ms、対ごとの時間短縮率中央値34.1%。場面ごとの内訳は計っていないため、特定処理の寄与は断定しない。
- 公式ツールの公開100件の固定仕事量比較では、全操作・仮想評価・最終得点が同一。最終出力時間の対ごとの短縮率中央値は全100件1.74%、終盤探索が稼働した16件1.86%。事前に設定した2%に満たず、同時間比較・新規ケースの採用試験には進めていない。

今後ライブラリ化するときは、役割重複・単独案件・予約済み・到着不能・同点を含む小さい入力で愚直な全直積との一致をテストする。候補生成だけでなく利用先の処理全体を測り、速くなった場合だけ既存の経路を置き換える。
