# AHC 汎用ライブラリの高速化提案

このファイルは、複数の問題に使えそうな高速化の提案と検証記録。問題固有の工夫は問題の実験記録に置く。使いにくかった点は [LIBRARY_FEEDBACK.md](LIBRARY_FEEDBACK.md)。
既存公開APIを壊さないこと、固定仕事量で正確性と処理速度を比較すること、実戦では同じ時間内の試行数・採用数・得点を区別することを基本にする。比較時の既定は GNU C++23、ソース内の最適化指定、追加の最適化フラグなし。計測時間が短ければ固定試行を繰り返し中央値も記録する。

## Aho–Corasick の高速な走査用表現

- 対象: `library/aho-corasick.hpp`。構築後に同じパターン集合で大量の文字列を走査するとき、遷移表・出力ID列の参照を平坦にし、1文字ごとのコンテナ呼び出しを減らす。
- 互換案: 既存の `add` / `build` / `advance` / `matches` は変更せず、任意の凍結済み走査ビューか、一括走査用APIを追加。文字の範囲、失敗遷移、重複ID・出力順・スキップ文字の取り扱いを維持する。メモリ使用量の比較も必要。
- AHC004での根拠: [研究用実装](https://github.com/tokotoko7777/ahc-workspace/tree/ab92268a8e84e7cfded2fe0f03cbda4473ed88a7) の平坦化・盤面配置・乱数呼び出しをまとめた変更は、追加最適化フラグなしの合成25,000候補で440.106msから155.406ms。候補・差分・乱数列が一致。**Aho単体の改善率ではない**ため、切り分けベンチの前に採用しない。
- 追加確認: ランダムパターン・重複・境界・リセットについて既存APIと愚直を比較し、一括走査の固定文字数で時間・ピークメモリを比較。現状は提案、共通ライブラリ既定動作は未変更。

## 循環ラインの文字・空きマスク

- 対象: 小さな盤面・文字列上で、同じ長さの循環位置候補を何度も比較する処理。各文字・空きセルをビット集合にし、回転させた集合の積で配置可能位置をまとめて求める。縮約した候補だけを列挙し、空き数などをpopcountで得る。
- API案: 読み取り専用の線マスクとセル更新の2操作を分け、配列極性（循環／非循環）・空きセルの意味・ビット幅の境界を明示する。適合しない幅には従来のスカラー経路を用意する。候補の列挙順を保存できるようにする。
- 検証中: AHC004のfillと候補走査で固定仕事量・同じ開始状態・同じ乱数列を突き合わせる。全て埋まった行で空きマスクを読まない高速経路も候補。測定と互換テストが揃ってから、共通部品として切り出すか判断する。
- 追加確認: 循環の折り返し、空きのない場合、全て空き、文字集合の端、ビット幅の上限、入れ替えや更新時のマスク整合性を愚直列挙と比較。候補が変わらない高速化と、探索方針の変更による得点増を分けて記録する。

### 密な状態の高速経路（一般化候補）

AHC004では固定試行の計測で、配置候補を総当たりする部分が主な負荷だった。
空きのない行では空きマスクの読み込みと集計を省くと、合成11条件で候補・採否・乱数・最終盤面は同じ。
長い9条件の合計時間中央値は従来比0.9125（約8.8%短縮）。
密な状態でだけ効き、疎な状態は既存経路を使う。AHC004の候補走査での結果であり、ライブラリ全体の改善率ではない。

### 追加案: 文字の有無で行・列を先に絞る

行・列ごとに各文字が存在するかを 64 bit のマスクに保持する。検索語に現れる異なる文字のマスクを交差させ、残った行・列だけを従来と同じ順番で位置照合する。更新では、文字の位置マスクがゼロをまたいだときだけ行・列ビットを変える。対象はトーラスに限らず、複数の短い列を横断して同じ語を探す場合。

合成 20×20 の 36,000 クエリで最初の一致行と開始位置マスクが一致。位置照合 1,333,311→535,412 回、事前絞り込みも含む論理積 2,905,711→1,512,757 回。別の愚直照合とも、幅 1〜20 の 126,000 行で一致した。これは演算回数のみで、準備・更新・候補走査を含んだ実時間や公式スコアの改善は未確認。文字がほぼ全行に現れる分布で逆効果にならないか、採用前に確認する。

追試（GNU C++23、交互に5回、中央値）: 長さ4/7/11の合成盤面で、クエリだけなら占有率25%で3.17〜3.95倍、65%で1.26〜1.64倍、100%で0.85〜1.05倍。巻き戻し可能な更新込みではそれぞれ3.24〜3.73倍、1.23〜1.74倍、0.87〜1.01倍。初期構築は18〜29%遅かった。愚直照合と更新の差分テストは一致。疎な状態のオプションとして検討し、密な状態や現行AHC004への一律導入は見送り。公式スコアは未測定。
[測定コードと再現手順](https://github.com/tokotoko7777/ahc-workspace/tree/5689d53601f89f3c6d6d031a672079525c8c291c/problems/ahc004/experiments/line_prefilter)。

## 進入費用が小さい格子での最短路前計算（AHC005）

各辺の費用が「移動先セルの正の費用」で、その範囲が1〜9と分かる格子では、10個の循環バケットで距離順に処理できる。ある頂点への進入費用はどの直前頂点からでも同じなので、初回の緩和で最短距離が確定する。最短距離が同じときは、元のヒープ版と同じ最小IDの直前頂点を選ぶ。迂回時に費用が変わる一般グラフ、0費用、上限の大きい場合はこの簡略化を流用しない。

旧ヒープ版と合成60マップで全端点距離、全セルの前駆、初期経路を照合して一致。固定作業でN=25/40/65は4.68/5.43/5.63倍、N=10は1.28倍。これは前計算のみ。各ケース全体の時間と探索回数、公式配布100件の得点への寄与は別に測る。既定のヒープ版を残す。

## 対称な距離表で前後2点の挿入を速くする（AHC006）

既存 `best_ordered_pair_insertion` の線形探索と同点規則は保持し、対称な距離表がある場合のみ、追加する2点の距離表行と前の位置で読んだ距離を再利用する。表なし・非対称・動的距離では既存APIを残す。2,048の合成候補で距離差とgapの組が一致。各307,200候補の固定作業を交互に6回測定し、挿入走査のみ旧1,950〜2,219 ms → 新414〜471 ms。約4.7倍はこの内側処理で、実行全体の速度や最終点とは別。汎用化するなら既存の距離コールバックは変更せず、行参照を任意で渡す別オーバーロードを検討する。

## 座標を成分別に並べる距離表の前計算（AHC006）

二次元の静的な整数マンハッタン距離表を作る場合、点の構造体を毎セル解釈する代わりに、X・Yを別々の連続配列に並べてから各行を生成する。通常の参照API・整数幅は変えず、距離の上限が格納型に収まる場合に限定。合成7板の28,028,007セルを直接式と照合してすべて一致。固定探索280,000スロットで提案・受理・出力も同一。前計算中央値85.108→10.390 ms（約8.2倍）で、削れたのは前計算のみ。座標から通常手の距離も逐次再計算する別案は固定探索で速くならず、同じ変更に含めない。
